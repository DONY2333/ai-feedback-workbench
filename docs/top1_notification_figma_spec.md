# Figma 原型规格：通知状态诊断

关联 [Mini PRD](top1_notification_mini_prd.md)；Issue `ISS-3955d4f6ed9d`。仅输出可照画的规格，不创建 Figma 文件。

## 范围与统一视觉

- **移动端 Android 概念原型**：L002、L003 明确涉及移动设备与安卓；不是全平台设计或现有飞书能力复刻。
- **严格 3 个 Frame**，画板均为 390 × 844 px；系统栏、顶部导航与底部安全区使用占位，不加品牌 Logo。内容使用 Auto Layout，超出可纵向滚动。
- 白底 `#FFFFFF`，页面次背景 `#F5F6F8`，主文本 `#1F2329`，次文本 `#646A73`，蓝色主按钮 `#3370FF`；绿色通过、橙色待检查、灰色未知。状态必须同时有 icon + 文案，不能只靠颜色。
- 使用系统无衬线字体；页面标题 20/28 semibold，区块标题 16/24 semibold，正文 14/22，辅助说明 12/18。页面边距 20 px，区块间距 24 px，卡片内距 16 px，圆角 10 px；主按钮高度 48 px。
- 交互与状态均为**产品方案示例，不是真实设备检测结果**。未检测、未知不显示为异常；本地检查通过不等于推送已恢复。
- 同一 Frame 内用组件 Variants 切换状态，不为成功、失败等状态另建第 4 个 Frame。不要添加用户画像、图表或业务收益数字。

## Frame 1：通知设置 / 诊断入口

**目的**：让遇到提醒异常的用户找到检查入口。

从上到下：

1. 顶部导航：返回 icon，标题「通知设置」。
2. 设置卡片：「消息通知」＋开启的开关；这是原型示例，不意味着用户反馈当时一定为开启。更改开关只影响原型状态，不模拟系统权限已改变。
3. 诊断卡片：标题「通知状态」；首次进入显示灰色「未检测」。辅助文案「如果消息提醒异常，可检查系统权限和后台状态。」
4. 蓝色主按钮「开始诊断」→ Frame 2 的检查中 Variant，完成后切结果 Variant。
5. 页底辅助文字：「本地设置正常，也可能存在其他通知问题。」

卡片可选 Variant（仍在 Frame 1）：已有可信检查记录时显示状态及「上次检测时间」占位。存在明确配置异常才显示「⚠ 检测到可能影响消息提醒的配置问题」；全部可读项通过显示「本地检查未发现异常」；有未读项显示「部分状态需手动确认」。不得凭空显示故障已定位。

## Frame 2：通知状态诊断

**目的**：展示已知、未知与下一步，不冒充根因定位。

顶部导航返回 Frame 1，标题「通知状态诊断」。顶部小字「以下为可检查的本地状态，不代表完整推送链路」。

检查中 Variant：三行状态为「检查中」，操作按钮暂不可点击；完成后原位替换，不跳新 Frame。

结果 Variant 采用三张紧凑卡片：

| 检查项 | 示例状态与简短原因 | 行内动作 |
| --- | --- | --- |
| App 内消息通知 | ✅ 已开启；「当前应用设置允许消息提醒」 | 「查看应用设置」展开本卡片的说明，不增加页面。 |
| 系统通知权限 | ⚠ 需要检查；「无法自动确认，请到系统设置核对」 | 「前往系统设置」。若技术上确实读到关闭，可切换为「已关闭」，并对应修改原因。 |
| 后台运行相关状态 | 灰色「无法自动确认」；「当前设备可能需要手动核对后台限制」 | 「查看检查方法」展开说明。只有具备可靠读取能力，才可改为“已确认受限”。 |

卡片间距 12 px，每卡含 icon、标题、文字状态、原因、动作；整体状态有未知时显示「部分状态需检查」，不显示“发现两个异常”。

底部按钮：次按钮「重新检测」；主按钮「去验证通知」→ Frame 3。

交互规格：

- 「前往系统设置」在原型中仅注释为系统外部跳转，不新增系统设置 Frame。用“返回应用”交互模拟回到当前 Frame，显示「已返回，请重新检测」；不直接宣布设置已修复。
- 「重新检测」先切检查中，再切预设结果；原型演示数据须标记为模拟。若全部可读项通过，显示「本地检查未发现异常；若仍收不到，请测试或提交问题」。
- 不可读项一直保留未知；无可修复项也可进入测试，不强迫用户修改权限。
- 「查看检查方法」按已验证的 OS/厂商说明填充，暂无技术确认时仅写占位说明，不编造真实系统路径。

## Frame 3：验证通知 / 继续排查

**目的**：核验本次操作结果，给未恢复用户明确出口。

顶部返回 Frame 2，标题「验证通知」。

默认文案：「完成设置检查后，可发送一条测试通知，确认本次是否能看到消息提醒。」只有复检确认设置改变后，才可将开头改为「设置已更新」；不得默认宣告修复完成。

默认状态：蓝色主按钮「发送测试通知」，次文字入口「跳过测试并提交问题」。辅助说明「测试方式与真实后台场景是否一致，需技术确认。」

同 Frame 内组件状态：

| Variant | 文案与操作 |
| --- | --- |
| 请求中 | 「正在发送测试请求…」；主按钮禁用，避免重复点击。 |
| 请求已受理／展示未知 | 「测试请求已受理。你是否看到了测试通知？」；提供「看到了」「未看到」两个按钮，不显示“已送达”。 |
| 用户确认看到 | ✅「你已确认看到本次测试通知」；说明「仅验证本次测试，不代表日常后台问题已解决」；主按钮「完成」→ Frame 1，卡片只记录本次测试确认。仍保留「日常仍异常？提交问题」。 |
| 发送失败 | 「测试请求未能发送，请稍后主动重试」；「重新发送」「提交问题」。不自动重试，不声称消息已到设备。 |
| 用户未看到 | 「仍未收到通知？」；「继续排查」→ Frame 2，或「提交问题」展开本 Frame 的提交区。 |

“测试通知已送达”不作为默认成功文案：仅在将来具备可靠设备展示回执且评审通过时，才可使用更强的系统确认状态；本版以用户确认示例为主。

提交区（折叠组件，不增加 Frame）：只展示待用户确认的本次检查摘要、设备/OS 信息占位及可选补充描述；标注不收集聊天正文。确认后点击「提交问题」，原位显示提交成功或失败；提交失败允许主动重试。这里是交互规格，不意味着现有客服接口、自动日志采集或工单能力已经实现。

## 连线与演示验收

主线：Frame 1 开始诊断 → Frame 2 查看结果／模拟设置返回与复检 → Frame 3 测试并确认。失败线仍只在这三个 Frame 的 Variants 与展开区中流转。

照画后演示两条路径：

1. **可确认配置异常**：诊断发现系统通知关闭 → 系统设置跳转占位 → 返回复检 → 测试请求受理 → 用户确认看到。
2. **本地正常或状态未知、仍未看到**：不要求重复改权限 → 测试 → 未看到 → 提交问题。此路径对应 L002、L038 提醒的方案边界，不声称已复现其技术根因。

验收重点：全程只有 3 个 Frame；未知不被标成关闭；发送受理不被标成送达；用户可退出或继续提交；所有效果与文案为方案设想，不能作为真实产品已上线证明。
