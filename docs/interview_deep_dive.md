# 面试深挖：38 个回答框架

回答按「观点→证据→边界」展开，不背诵未完成能力。数值来源见[实验总结](../evaluation/results/experiment_summary.md)与[项目案例](project_case.md)。

## 1. 为什么选择用户反馈分析？

- 核心观点：反馈到需求之间存在筛选、归类和证据断层，适合验证 AI 产品闭环。
- 项目证据：已串联评论、Issue、Top 5、Mini PRD。
- 风险/限制：是需求假设，未测真实团队节省工时。

## 2. 用户是谁？

- 核心观点：预期是产品经理和产品运营，需要批量理解反馈并回溯。
- 项目证据：四页围绕反馈、质量和洞察组织。
- 风险/限制：没有已验证用户规模或画像研究。

## 3. 为什么不是直接让 ChatGPT 总结？

- 核心观点：摘要可以辅助，但不能替代稳定结构、Gold 验证和逐条证据链。
- 项目证据：八字段 JSON、ID 映射及原文下钻。
- 风险/限制：没有对 ChatGPT 做受控对照，不声称一定优于它。

## 4. 这个产品真正解决什么问题？

- 核心观点：让反馈到需求的过程可检查，而非仅让文本变短。
- 项目证据：Issue 可追到全部原文，模型有独立评价。
- 风险/限制：需求建议仍需产品判断。

## 5. 最有价值的功能是什么？

- 核心观点：证据追溯与质量边界结合，允许发现并纠正错误结论。
- 项目证据：Top 1 五条证据及 Holdout 错误样本都可查。
- 风险/限制：可追溯不等于已证明结论正确。

## 6. Prompt V1 最大问题是什么？

- 核心观点：输出契约与人工标签不统一，尤其模块自由文本。
- 项目证据：历史模块仅 1/20 Exact Match。
- 风险/限制：不是模型理解能力只有 5%。

## 7. V1 到 V2 改了什么？

- 核心观点：固定 19 类模块，对齐正式类型、严重程度及基础定义。
- 项目证据：模块 18/20，但类型 18/20 降到 16/20。
- 风险/限制：包含任务定义变化，不能当纯能力提升。

## 8. V2 到 V3 为什么改？

- 核心观点：根据明确边界错误做小修。
- 项目证据：补 Bug/困难、后文修正、具体短文本有效及模块映射，类型到 19/20。
- 风险/限制：无消融实验，不能归因于某一条规则。

## 9. 为什么不继续做 V4？

- 核心观点：冻结版本后验证泛化，并控制项目范围。
- 项目证据：Holdout 分析只报告错误，没有修改 V3。
- 风险/限制：已看过 Holdout，再调需要新独立测试集。

## 10. Prompt 调优和模型微调有什么区别？

- 核心观点：前者改输入约束和例子，后者用训练数据更新参数。
- 项目证据：本项目仅 Prompt 迭代，没有训练模型。
- 风险/限制：小 Gold 适合先验证任务契约，不足以证明微调必要。

## 11. Gold Set 怎么做？

- 核心观点：读取已有人工标注 Excel，明确列映射、ID 和正式标签。
- 项目证据：82 条，包含有效性、类型、模块、痛点和严重程度人工列。
- 风险/限制：没有完整多人独立标注与裁决记录，不虚构流程。

## 12. 为什么要 Dev/Holdout？

- 核心观点：把调规则与检验泛化分开。
- 项目证据：Dev L001–L020；Holdout L021–L043 + W001–W039。
- 风险/限制：Dev 全是飞书，分布不均衡。

## 13. Accuracy 和 Macro-F1 为什么差那么大？

- 核心观点：Accuracy 受大类支配，宏平均每类等权。
- 项目证据：模块 80.65% 对 55.39%；固定 19 类仅 14 类有 Gold，空类零分进入分母。
- 风险/限制：差距不能全归因于已覆盖长尾类错分。

## 14. Severity 为什么表现较差？

- 核心观点：影响程度有语义歧义，同时类别极不均衡。
- 项目证据：高→中 11；高31、中13、低0，始终猜高也为 70.45%。
- 风险/限制：没有验证低类能力，需标注与样本补强。

## 15. 为什么核心痛点没有 Exact Match？

- 核心观点：同一含义可有多种措辞，字符串不同不必然错误。
- 项目证据：本轮保存 Gold 与预测但不算准确率。
- 风险/限制：尚未建立语义评价或人工 rubric。

## 16. 什么是 Evaluation Overfitting？

- 核心观点：看测试错误再反复定规则，使成绩适配样本而非真实分布。
- 项目证据：Dev 用于 V1→V3，冻结后才跑 Holdout。
- 风险/限制：划分并不能完全消除小样本或分布偏差。

## 17. Holdout 看过以后为什么不能继续用？

- 核心观点：可以回归检查，但不能再宣称针对其调优后的成绩是完全未见泛化。
- 项目证据：本轮分析错误但不建 V4。
- 风险/限制：未来须另采 pristine unseen test set。

## 18. 为什么本地 Evaluation 后还需要 Langfuse？

- 核心观点：本地确定口径，平台管理调用、版本与可观察性。
- 项目证据：正式三版各20条，Generation 与294个 Scores 关联。
- 风险/限制：平台可见不意味着评价方法天然正确。

## 19. Trace / Dataset / Experiment / Score 分别是什么？

- 核心观点：Trace 是调用链，Dataset 是固定样本，Experiment 是版本运行，Score 是评判值。
- 项目证据：feedback-dev-20、三个 final-r3、五类适用 Gold Scores。
- 风险/限制：不适用 severity 不写分，不能补零。

## 20. C0/C1 解决什么问题？

- 核心观点：C0 验证三版链路，C1 隔离历史后处理并验证回放。
- 项目证据：raw_output、normalized_output、score_input 独立保存。
- 风险/限制：历史源码不全，三版均 partial reproduction。

## 21. 为什么 V1 normalization 污染严重？

- 核心观点：把输出先改成 Gold 值，会造成假正确并破坏版本对比。
- 项目证据：L001 自由模块不能被映射成其他后计对，修正后 module=0。
- 风险/限制：存档回放一致不代表所有原始异常分支完整复原。

## 22. Issue Clustering 怎么做？

- 核心观点：产品+预测模块粗分，再用保守问题锚点和相同长痛点规则归并。
- 项目证据：63条、24组、54候选；每条主 Issue 唯一且可追原文。
- 风险/限制：不是 LLM/embedding 语义聚类，可能碎片化。

## 23. 为什么不用 KMeans？

- 核心观点：当前量小且有跨产品、模块不能误合并的约束，先保证可解释。
- 项目证据：54候选中不确定保留单条，未训练向量聚类。
- 风险/限制：规则召回有限，并未实验性证明优于 KMeans。

## 24. Top 5 怎么排？

- 核心观点：结合重复证据、预测严重程度、核心场景及样本竞品背景。
- 项目证据：四个多成员优先，第五补高严重程度单条换机验证循环。
- 风险/限制：不使用虚构商业分值，排序仍有判断性。

## 25. 为什么 Top 1 选通知问题？

- 核心观点：证据最多且影响即时通信核心任务，可自然进入小范围设计。
- 项目证据：5条，预测高4中1；通知模块6/31。
- 风险/限制：不是独立用户规模或真实故障率。

## 26. 怎么证明建议不是 AI 瞎编？

- 核心观点：事实必须有成员评论，方案单独标注为设计推断。
- 项目证据：Top 1 五个 ID→Mapping→原文；已调权限仍失败的反例保留。
- 风险/限制：方案合理不等于可行或有效，仍需验证。

## 27. 能据此判断飞书和企业微信谁更好？

- 核心观点：不能，只能描述当前采集样本的集中问题。
- 项目证据：问题反馈31对32，来源与分布未控制。
- 风险/限制：选择偏差和缺少用户基数，不可推总体质量。

## 28. Notification Health Check 为什么值得做？

- 核心观点：将模糊故障转成可理解的检查、引导、验证与提交路径。
- 项目证据：五条症状证据支持排查需求，不证明共同根因。
- 风险/限制：价值是假设，不能替代底层推送修复。

## 29. 它有什么风险？

- 核心观点：同症异因、系统状态不可读、测试条件不等于真实后台。
- 项目证据：L002 已配后台权限仍收不到，是权限万能论反例。
- 风险/限制：本地正常不等于链路正常，请求受理不等于送达。

## 30. 系统无法读取某项权限怎么办？

- 核心观点：显示无法自动确认，提供手动核对及继续提交，不假装检测成功。
- 项目证据：PRD 规定未知、明确异常和本地未发现异常三种边界。
- 风险/限制：OS/厂商适配与跳转需技术评估。

## 31. 上线后怎么判断需求成功？

- 核心观点：先定义流程和代理指标，再看相关负反馈，需可信埋点。
- 项目证据：诊断完成率、配置异常解除率、测试通知用户确认率，均无当前值。
- 风险/限制：用户确认不是可靠送达遥测，不能冒充故障修复率。

## 32. 为什么 API 401 时 fail-fast？

- 核心观点：鉴权系统性失败不能靠逐条重试修好，应及时停止。
- 项目证据：早期正式批次首条401便停止；离线测试覆盖。
- 风险/限制：避免日志暴露凭据，修配置后新建运行。

## 33. timeout 为什么不能直接终止整个 batch？

- 核心观点：单项临时故障不必否定其他样本，有限重试后明确记录失败。
- 项目证据：r3 对 timeout/429/5xx 允许一次显式重试，两次失败继续。
- 风险/限制：需同时报告失败数，不能只报成功样本准确率。

## 34. 为什么不让 SDK 自动无限重试？

- 核心观点：SDK 默认重试不是无限，但隐藏重试不利于精确预算和归因。
- 项目证据：max_retries=0；执行器每项最多2次，逐 attempt 计数。
- 风险/限制：r3 实际零 retry，异常分支主要靠离线测试验证。

## 35. 项目最大不足是什么？

- 核心观点：数据与验证覆盖不足，而不是页面数量不够。
- 项目证据：82 Gold、低类0、模块5类无覆盖，整条正确仅59.68%。
- 风险/限制：不能当生产能力或市场结论。

## 36. 再给两周会做什么？

- 核心观点：优先新独立样本、模糊标签复核和 Top 1 用户/技术验证。
- 项目证据：当前弱项已明确，方案仍概念级。
- 风险/限制：这是未来选择，不是已实现内容。

## 37. 100万条反馈怎么扩展？

- 核心观点：需要批处理、队列、去重、缓存、可恢复任务和分层抽样评测，再评估语义检索。
- 项目证据：当前本地 pandas 与顺序调用只适合 MVP。
- 风险/限制：未做百万级压测、数据库或分布式实现，不承诺吞吐。

## 38. 82条太少怎么回答？

- 核心观点：承认这是验证方法闭环的小样本作品，而非业务级性能结论。
- 项目证据：披露 Support、分母、弱项和已见 Holdout，不做显著性声明。
- 风险/限制：扩充来源、类别与独立标注后才可提高外推可信度。
