## 6. Precision / Recall / F1

### 计算口径

Precision = TP/(TP+FP)，Recall = TP/(TP+FN)，F1 = 2TP/(2TP+FP+FN)。
Support 是人工 Gold 属于该类的样本数，另输出 `predicted_support` 区分模型预测频数。
有效性的总览 Precision/Recall/F1 以 True 为正类，Support 为 49；总样本数仍为 62。

Macro-F1 按完整固定标签集合等权平均：有效性 2 类、反馈类型 5 类、产品模块 19 类、严重程度 3 类。
零分母使用 `zero_division=0`；Support=0 的类别在宏平均中按零值计算。
Weighted-F1 按 Gold Support 加权。无 Gold 样本的类别在单类 CSV 中 Precision/Recall/F1 留空，并标注“未覆盖”，不能把该类数值零理解为实测能力。
例如严重程度 Macro-F1 的分母为 3，包含未覆盖的“低”；它并不意味着已测试低严重程度的识别能力。

严重程度只排除 Gold 为“不适用”的行。若 Gold 为高/中/低而 Pred 为“不适用”，仍计错，并在混淆矩阵额外保留该预测列，不会被静默丢弃。
本次 Holdout 的 44 条适用样本没有这种预测不适用的情况。

## 8. Main Findings

1. 有效性区分在本批 Holdout 上较稳定（61/62），但不能外推到未覆盖的评论来源和表达方式。
2. Bug Recall 为 96.67%，使用困难 Recall 只有 54.55%。使用困难 11 条中 5 条被预测为 Bug，反映两类边界仍有混淆。
3. 安装/更新 10 条中 3 条被预测为性能/稳定性，另 1 条被预测为账号/登录/验证。该模块 Recall 为 60.00%，模块归类不宜只依赖表层故障词。
4. 严重程度 13 次错误全部是向较低等级预测：11 次高→中、2 次中→低。高严重程度漏判为中占 11/31=35.48%，对需要优先处理高风险反馈的场景尤其重要。
5. 单字段准确率并不等于整条结构化标签可直接使用：Holdout 完全正确率仅 59.68%，应保留人工复核。

这些是错误方向的统计描述，不足以证明错误来自 Prompt 的某一具体语句或模型的某种内部原因。

## 9. Limitations

- 人工 Gold Set 仅 82 条，Holdout 62 条；小样本造成的波动大，没有置信区间或显著性结论。
- 严重程度类别高度不均衡：“低”在完整 82 条中仅 1 条，且处于 Dev；Holdout 中为 0。不能仅依据 Accuracy 判断该任务能力，也不能声明已验证低严重程度识别能力。
- 模块中五类未覆盖，多类仅 1–2 条；小 Support 下的 100% 不代表稳定表现。Macro-F1 的固定标签口径需与覆盖率一同解读。
- Dev 全部来自飞书，Holdout 含两款产品，分布并非可交换的随机样本。不能将 Dev/Holdout 差异全部归因于过拟合。
- 未测量人工标注者间一致性，也未独立裁决模糊案例；Gold 标签可能含主观边界。
- 核心痛点是自由文本，本报告没有用字符串准确率评价；用户场景、证据质量、情绪倾向亦不在本轮自动指标范围。
- 已有明细只保存处理后的输出，不能据此评价原始 JSON 成功率、请求稳定性、延迟、成本或重试影响；未做重复运行以测量随机波动。
- Holdout 已经在本轮被查看和分析。今后若再针对这些错误调 Prompt，就不能继续把这 62 条称为完全未见测试集；应将其视为已见分析集。

## 10. Next Steps

1. 冻结本次 V3、预测结果和本报告，保留为历史基线。本轮不修改 Prompt。
2. 人工复核高→中、使用困难→Bug、安装/更新→性能/稳定性的例子，确认标注边界；仅记录争议，不在本报告中改 Gold。
3. 在下一轮另行采集独立、未用于调 Prompt 的测试集，补足低严重程度、未覆盖模块，并覆盖两款产品及不同语言/短评场景。
4. 若批准继续迭代 Prompt，使用 Dev 和已见错误做开发验证；在新的独立测试集上只做冻结后的最终验证，版本和样本 ID 要留档。
5. 产品使用时对高风险反馈和边界类保留人工审核，综合报告单类 Recall、F1、覆盖率和整条正确率，不只看 Accuracy。
